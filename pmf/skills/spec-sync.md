# spec-sync

目标：把一次代码改动映射到**受影响的 AC 清单**，然后强迫做一次判断。它不生成文档，也不自动改文档。

这是治 S1（review 结论不落盘）的抓手：结论必须落在某条 AC 上，否则无从检验。

## 1. 取改动范围

优先用 git；没有 git 就用用户给出的文件清单：

```
git diff --name-only HEAD~1     # 或 git diff --name-only
```

## 2. 三条定位路径

按代价从低到高试：

| 路径 | 做法 | 何时有效 |
| --- | --- | --- |
| 代码锚点 | `grep -rn "spec: " <改动文件>` | 模块入口有过锚点 |
| 测试引用 | `grep -rl "<改动文件>" docs/specs/*/spec.md` | AC 已挂 `test:` |
| 工作项 | `grep -rl "<工作项 ID>" docs/specs/` | 知道编号 |

三条都没命中，说明这块代码**没有任何 spec 锚点**——此时不要凭空补一份 spec，只报告「无覆盖」并建议补锚点。

## 3. 逐条判断

对每条受影响的 AC，只问一个问题：**这条描述现在还是真的吗？**

| 结论 | 动作 | 禁止 |
| --- | --- | --- |
| 仍然为真 | 更新 frontmatter `verified_at: <当前 sha>` | 不要重写措辞，会产生无意义的 diff |
| 部分变了 | 改这条 AC 的描述，或拆出新 AC | 不要悄悄改语义、保留 ID |
| 整条不成立 | 标 `[-]` + ADR + 该 spec 转 `retired` | 不要直接删行 |
| 范围整体变了 | 造新 spec，旧的 `retired` | 不要就地重写 Outcome |

判断不出真假的，**不要猜**——把它列进报告的「待确认」，让用户回答。猜出来的「已对齐」比不对齐更糟。

## 4. 补测试引用

行为变了但证据没变，是最隐蔽的失效。检查：

- AC 仍是 `[x]`，但它的 `test:` 指向的用例已经被改/删 → 必须更新引用或改回 `[ ]`。
- 新增了行为但没有 AC → 先判断它是不是本次范围内。不是就**不要**顺手加 AC（那是新工作项）。

## 5. 收尾

```
pmf_check          # 必须 0 error
pmf_evidence       # 受影响的 spec 是否仍 PASS
```

## 6. 回报

```
受影响的 spec：<ID> — <标题>
  AC-2: 仍为真 → verified_at 已更新
  AC-3: 部分变了 → 描述已改（原：… 现：…）
  AC-5: 不成立 → 已标 [-]，新增 ADR-0008
  AC-7: 待确认 → 需要你回答：<一个具体问题>
无覆盖的改动：src/foo.ts（无 spec 锚点）
```

## 硬规则

- 不判断就不改。猜「大概对齐」是本 skill 最大的失败模式。
- 一次只处理与本次 diff 有关的 AC，不顺手整顿其他文档。
- 改语义必须留痕：要么拆新 ID，要么标 `[-]` 配 ADR。
- 不新增 spec。要新 spec 就走 `spec-write`。
