# 落地路径与度量

框架失败的方式通常不是「设计不对」，而是「第一天报错太多，第二周被 `--no-verify` 绕过，第三周没人再提」。本文定义一条不会在第二周死掉的引入路径。

## 1. 三条原则

1. **先冻结，再治理**：引入前先停止新增野生文档，否则边治理边泄漏。
2. **只对新增违规阻断**：存量债进 baseline，不清算历史。
3. **触碰即治理**：一个存量文档只要被修改，就必须当场达标。

## 2. 三阶段

### 阶段 A：冻结（1-2 天）

- 建立 `docs/` 骨架、`templates/`、`pmf.config.json`。
- 写入 `README.md`（人写导航）与 `GLOSSARY.md`（先收 10 个术语）。
- 跑一次全量扫描，产出 `docs-baseline.json`。
- CI 挂检查器，**只对 baseline 之外的新增违规失败**。
- 在 `AGENTS.md` 加一段：新文档一律进 `docs/`，必须带 frontmatter。

**退出条件**：新增文档 100% 带 frontmatter；CI 不因存量债失败。

### 阶段 B：收口（2-4 周，增量）

不迁历史文档，只做一件事：**让新工作项走完 close gate**。

| 优先级 | 对象 | 理由 |
| --- | --- | --- |
| 1 | 当前活跃工作项的 spec | 直接解决 P3 |
| 2 | 正在被改的 design | 解决 S3 |
| 3 | 被删减的功能 | 转成 ADR，解决 S2 |

其余文档**不动**。等孤儿检测把它们捞出来。

**退出条件**：活跃工作项 100% 有 spec；关闭时 AC 落成测试的比例 ≥ 90%。

### 阶段 C：删除自动化（持续）

- 打开 `retention`：**先跑 `fixed` 模式**，只算不删，确认固定值与退役链路本身没问题。
- 稳定后再 `retention --enable-dynamic`，观察 `RETENTION.md` 里的 λ 与样本数；冷却期内实际仍走 fixed。
- 打开 `expire`，以每周一次的删除 PR 形式运行。
- 打开 `docs-debt` 周报，按 owner 派单。
- 打开「生成文件禁止手改」检查。

**退出条件**：连续 4 周到期未删率 < 5%；文档净增 ≤ 0。（若仍处 `fixed` 模式，以删除链路稳定运行为准。）

## 3. 唯一必须做的三件事

按此顺序，做不完就不做后面的：

1. **新文档必须带 frontmatter**。性价比高于后面所有工具之和。
2. **关闭时每条 AC 必须有测试，或转成 ADR**。这让「实现与预期是否一致」第一次成为可回答的问题。
3. **打开自动删除**。前两条只是加约束；不做这条，仓库仍然会涨——只是涨得更整齐。

## 4. 度量

| 指标 | 采集 | 健康的形状 |
| --- | --- | --- |
| 到期未删率 | `expire --dry-run` | < 5% |
| 退役区存量 | `retention` | 在 `N_target` 上下波动，不单向增长 |
| 复活率 | 索引中 `revived_at` | < 10%（更高说明 `R` 太短） |
| 测试承载率 | `check-evidence` | ≥ 90% |
| 墓碑空承接率 | `TOMBSTONES.tsv` | 低；升高说明删除门在放水 |
| 文档净增 | 索引 diff | ≤ 0 |
| `[-]` 占比 | spec 内统计 | < 20% |

> **不采集**「文档覆盖率」「文档字数」。前者可造假，后者与质量负相关。

## 5. 失败模式与对策

| 失败模式 | 症状 | 对策 |
| --- | --- | --- |
| 报错洪水 | 第一天几千条 | baseline + 只报新增 |
| 绕过 | `--no-verify`、改 ignore | ignore 条目带 `expiresAt`，到期报错 |
| 形式化填空 | frontmatter 齐全，内容全占位 | `TODO`/`待补` 设 warn；抽样 review |
| **不写测试** | AC 全部靠 `[-]` 关掉 | 监控 `[-]` 占比；> 20% 时停下来查测试设计 |
| **删得太早** | 复活率上升 | git 可恢复 + 墓碑 + 每份文档允许复活一次；连续复活则调大 `N_target` |
| 治理变项目 | 花在治理上的时间超过写代码 | 冻结机制数量：新机制需 ADR，且必须删掉一个旧机制 |
| 无人负责 | 文档债长期挂账 | `owner` 必填 + `DEBT.md` 按 owner 派单 |
| 无限延期 | unmet 全写成 follow-up | unmet 只有三个出口：立刻做 / 标 deleted / 明确拒绝 |

## 6. 谁维护

- 框架 owner：fairy，负责检查器、模板、保留期参数。
- 文档 owner：按域分配，写在 frontmatter `owner`。
- 复审节奏：每两周一次，只看 `DEBT.md`、`RETENTION.md` 与复活率。

## 7. 引入成本估算

| 项目规模 | 阶段 A | 阶段 B | 阶段 C 稳态（每人每周） |
| --- | --- | --- | --- |
| < 50 份文档 | 半天 | 3 天 | < 15 分钟 |
| 50-200 份 | 1 天 | 2 周 | 30 分钟（含删除 PR review） |
| > 200 份 | 2 天 | 4-6 周 | 1 小时 |

稳态成本主要是**看删除 PR**，这部分不能省——省了就等于把删除权交给脚本。若超过每人每周 1 小时，说明机制太多，应当精简而不是坚持。
