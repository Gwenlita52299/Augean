# Project Memory Framework — PRD

## 一句话

让项目目录下的文档**按需而生、按时而死**：活着的能被找到，死掉的能被删掉，行为由测试承载而不是由文档描述。

## 1. 背景

spec-driven development 把文档提到了执行入口的位置：先写 spec，再据 spec 实现。但文档一旦成为一等工件，就同时继承了软件的债务属性——会过期、会重复、会分叉、会没人删。

当前项目里的表现（4 类现状）：

| # | 现状 | 本质问题 |
| --- | --- | --- |
| S1 | 需求与实现未对齐时，review 完的结论只存在于对话里，没有落盘 | 决策无载体，下次重新讨论 |
| S2 | 功能点被删减后，文档不跟着改，spec 描述的是不存在的系统 | 文档无失效机制 |
| S3 | 初期设计不全面，后续推翻，旧文档既不删也不标记 | 文档无版本语义 |
| S4 | 为了让人看懂 AI 实现的架构，要求生成 HTML 讲解；但该 HTML 不随实现更新，实际成了描述旧版本的短期文档 | 生成物的**生产成本低、维护成本被忽略**，于是以「长期文档」的身份存在 |

S4 是本轮明确的关键现状。它的教训不是「HTML 不该生成」，而是：**重构成本低的产物，寿命必须短**。一份能一键重建的讲解，合理处置是「重建或删除」，而不是「保留并逐渐失真」。

对应 4 个痛点：

| # | 痛点 | 现在的土办法 | 为什么不够 |
| --- | --- | --- | --- |
| P1 | 文档堆积，未及时清理 | 靠人记得删 | 没人对「删」负责，删了还有引用断链风险 |
| P2 | 命名与路径不统一，散落各处 | 约定俗成 | 约定不进工具，就没有约束力 |
| P3 | 想找某需求的 spec 找不到 | 全局搜索关键词 | 搜索依赖记忆关键词，且不知道「哪份是当前有效版」 |
| P4 | 类似的实验/脚本重复造 | 复制粘贴 | 没有「已做过」的登记处，复用无从发生 |

## 2. 目标

1. **可定位**：活着的 spec 3 步内可达；已关闭的工作项，1 步内找到承接其行为的测试。
2. **可判死**：每份文档有机器算出的到期日，到期自动删除，不需要人记得。
3. **可对账**：spec 的验收标准必须落成可执行测试，而不是再写一份解释文档。
4. **可复用**：做过一次的实验、脚本、决策，有登记处且能被下次检索到。
5. **总量可控**：活跃文档数被保留期公式锁在常数附近，不随项目时长单调增长。

## 3. 非目标

- **不做**长期文档档案。没有 archive 区，退役即删除（见 [ADR-0001](../decisions/0001-spec-as-snapshot.md)）。
- **不做**叙述性回溯保障。删除后要读原文，去 git 历史里找，框架不负责。
- **不做**通用文档站/知识库产品，不替代 Notion、Confluence。
- **不做**全文语义搜索；检索依赖结构化元数据 + 索引。
- **不自动生成**文档内容；框架只保证结构、链接、状态、寿命正确。
- **不做**跨仓库文档联邦（第一版假定单根）。

## 4. 核心设计主张

1. **代码是 ground truth，测试是承重墙**：能写成测试的知识，不写成文档。
2. **文档是脚手架**：按需搭、按时拆。默认结局是删除，不是留存。
3. **寿命由产出频率与重构成本共同决定**：动态计算，写在工具里而非文档里（见 [03 §4](03-lifecycle.md)）。
4. **ID 优先于路径**：文档有稳定 ID，路径可变，引用走 ID。
5. **删除留墓碑，不留正文**：一行 `TOMBSTONES.tsv` 记录「它曾经存在、行为现在在哪」。
6. **索引一律生成**：手写索引必然漂移（参考仓库已有实证）。
7. **默认保守，动态是显式选择**：保留期默认用固定值；开启动态只统计开启之后的数据，且从不回溯已定的删除日期（[03 §4.6](03-lifecycle.md)）。

## 5. 成功指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| M1 定位步数 | 从一个需求/模块到当前 spec 或承接测试的操作步数 | ≤ 3 |
| M2 到期未删率 | 已过保留期仍未删除的文档占比 | < 5% |
| M3 测试承载率 | close gate 时 AC 有对应测试的比例 | ≥ 90% |
| M4 重复造轮率 | 同类实验脚本重复实现次数（月度采样） | 连续 2 个月为 0 |
| M5 文档净增 | 每月新增 − 删除 | ≤ 0 |
| M6 生成物新鲜度 | explainer 的 `source_sha` 落后 HEAD 的天数 | ≤ 其保留期 |

## 6. 范围

**第一版必须做**（MVP）：
- 目录契约与命名规则（[02](02-design.md)）
- 7 类文档模板 + frontmatter schema（[04](04-spec-contract.md)）
- 生命周期 + 保留期计算器，含默认关闭的动态开关（[03](03-lifecycle.md)）
- 三个检查器：frontmatter、索引一致性、AC→测试核对（[05](05-tooling.md)）

**第一版不做**：
- 自动从代码生成 spec
- 文档 GUI 浏览器
- 跨仓库联邦

## 8. 被接受的代价

如实记录三条，避免后续把代价当缺陷：

1. **失去叙述回溯**：spec 删除后，「当时怎么想的」只能靠 ADR 与 git。ADR 只记不可逆决策，日常推演不会留痕。
2. **对不写测试的项目不成立**：快照派的前提是 AC 能落成测试。若某类需求（纯视觉、主观体验）落不成测试，必须给它一个出口。
3. **删除不可逆地改变仓库**：虽然 git 可恢复，但恢复需要人知道去哪找。
